# 架构模式：按规模和职责选「活法」

> 适用场景：项目超过 3 个角色 / 计划做游戏 / 要长期改时读。
> 下面每一档都是**社区作品里真实存在的做法**（做法本身才是经验；具体某个作品有几块积木不重要，
> 想核就自己用 `lab/inspect-sb3.mjs` 量）。
>
> **先读这一条**：Scratch 里角色之间**没有函数调用、没有共享局部变量**。所以"多拆一个角色"的
> 真实代价不是文件数，而是**这段代码从此只能复制**。切角色的完整决策（含三种真实切法的数据对比、
> 跨角色共享代码的三条路）在 **sprite-split.md**；本篇只讲"选哪一档架构"。

## 按规模选架构（先想清楚你要哪种）

### Level 1：算法演示（几十块以内）
一个角色一个绿旗脚本完事。比如「用十几块实现缓动旋转」。**别过度设计**——不需要广播、不需要引擎。

### Level 2：功能游戏（几百到一千多块）
4-6 个角色按**职责**分：
- `System`（初始化/时钟）、`Player`、`Enemy`、`Danmaku`（弹幕克隆池）、`Hitpoint`（碰撞判定）
- 东方 style 弹幕就是这个结构：模块间广播，各自 forever+wait 主循环
- **角色命名按职责不按默认名**（Sprite1 ❌）

### Level 3：系统游戏（几千块）
开始需要**分层**和**专用模块**：
- 图层精灵组：`图层//前 / 中前 / 中后 / 后`——每层一个角色管一层的排序
- 专用子系统独立成角色：`存档`、`死亡界面`、`商店`、`检测Fps`、`过渡`（转场黑幕）
- 状态机变量：`page`（当前页）、`mod`（模式）、`target.page`——**用变量显式记录状态**，别靠「现在谁显示着」隐式判断

### Level 4：引擎派（上万块，慎入）
三种真实存在的极端做法：

**A. 逻辑 / 绘制 / 库 三角色**（这一档里最推荐）
- 一个**逻辑角色**：装所有实体（克隆体）+ 所有规则
- 一个**绘制角色**：只有 **1 张造型**，专门用画笔把东西画出来（投影、线、圆、HUD）
- 可选一个**库角色**：只放"画一条线 / 画一个圈"这种最底层积木，别的角色 `广播并等待` 来调

为什么必须把绘制单独拆出来：**绘制顺序**。多个角色往同一支画笔上画时"谁先画"取决于线程顺序，
你控制不了；集中到一个角色以后，顺序 = 脚本顺序。（画笔的颜色/粗细/落笔状态每个角色各有一套，
所以不会串色 —— 串的是**先后**。）
真实样本：`Sprite`（规则 + 85 张造型）/ `Renderer`（1 张造型，最大单块 782 块）/ `CDPen`（1 张造型，只画冷却圈）。
另一个 14461 块的作品是它的变体：`关卡运算模块`（12669 块）+ `地图生成模块` + `显示模块`（116 块 + 165 张造型）。

**B. 三精灵引擎**（RENDER / MAIN / LOADER + canvas 扩展）
- RENDER：只管画（pen + canvas）；MAIN：只管逻辑（列表就是它的内存）；LOADER：只管序列化（解析文本存档码）
- 适合：工具类作品（词曲渲染、编辑器）。和 A 的区别只是把"读取/还原"也拆了出去。

**C. 单精灵 ECS**（`Ent` 装全部实体逻辑 + `Draw` 专用渲染 + SFX + UI）
- Ent 一个角色装下所有实体：几百个 top-level 脚本、上百个全局变量
- 相机系统：`Cam X/Y/Zoom/Rotation/Focus` 全局变量
- 输入系统：双击检测、按住时长、滚轮状态全部做成全局变量
- 适合：真正的 RPG / 大世界。**这是「能跑」的天花板，也是维护噩梦**——上百个全局变量谁都不敢改。
  AI 不到万不得已别学这套；真要做大世界，用**列表分组**把全局变量压回几十个以内

## 通用铁律（各档位作品都这么做）

1. **初始化集中制**：一个 `_ Init` 广播，所有模块监听并复位自己的变量。绿旗重开必须回到初态（这是社区检验作品的暗标准）。
   **角色一多就得分批**：`广播并等待` 会把所有接收方挤在同一帧里跑完，40 个角色的初始化 = 一帧干完 = 开场掉帧。
   做法是"一个角色一个 `init-<名字>` 广播、中间隔 `等待 0 秒`、用计数器驱动进度条" —— 见 **boot-pipeline.md**。
2. **广播命名即架构文档**：`_ Init` / `Start Game` / `__ PL Inv`（`__`=系统级、`_`=模块内部）。看广播列表就能画出系统图。
3. **自定义积木是唯一防重复手段 —— 但它只在所属角色内可见**。两个角色要同一段逻辑，只能复制粘贴
   （广播调用不算，参数得走全局变量）。所以：**能放进同一个角色就别拆**；真复制了，就加编号前缀
   （`40检测x`）+ 同名返回槽（`out40*地面h`），改的时候记得每一份都要改。
   实测 9 个作品 65 组跨角色复制件里 **49% 已经不一致** —— 这不是理论风险。
4. **列表前缀 = 命名空间**：`graph.point`、`graph.link`、`graph.chosen_point` 同属一个结构域。
5. **图层控制显式化**：入场时 `移到最前`，别依赖创建顺序（那是隐式地狱）。顺序要求严格的，索性全部绘制集中到一个角色（Level 4 A）。

## 反面教材（样本里真实存在的坏味道，AI 别学）

- ❌ 默认名满天飞：`Sprite1`、`角色1`、`变量1`——重命名是零成本的第一步
- ❌ 一个 forever 塞一两百块：拆 procedure，主链保持 10 块内
- ❌ 逻辑和渲染混在一个链里：改个动画效果要碰游戏逻辑——分角色/分 procedure
- ❌ 几十个变量叫 `_temp`、`temp2`、`:value`：临变量泛滥=没想清数据模型，该用列表结构化
- ❌ 魔法数直写：`移到 x:(47) y:(-123)` 到处复制——常量集中初始化
- ❌ 检测不到退出条件的等待：`等待 1 秒` 硬编码卡时序，改用广播信号量

## 什么时候该停下来简化（给 AI 的自觉）

- 角色 > 15 个且互相广播成网 → 该合并成「模块精灵 + 列表」（拆到 64 个角色的作品，最大的一个广播有 **27 个接收方**，每发一次就是 27 条线程重建）
- 全局变量 > 30 → 该换列表结构体
- 同一个 forever 里 if 嵌套 > 3 层 → 该拆 procedure 或换状态机变量
- 复制粘贴的块组 > 2 份 → 该包自定义积木；**如果这 2 份在两个角色里，先问能不能合并角色**（否则从此只能手同步）
- 两个角色都在维护"同一件事"的状态 → 一定会打架，趁早并成一个

选不定的时候按这个顺序问：① 这东西的造型要一起换吗（要 → 角色，不要 → 列表）；
② 数量会超过 300 或每帧上几百吗（是 → 列表）；③ 这段逻辑只有一个角色用吗（是 → 放它自己身上）。
完整的判据和真实数据在 **sprite-split.md**。
