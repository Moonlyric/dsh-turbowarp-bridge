# 架构模式：按规模和职责选「活法」

> 适用场景：项目超过 3 个角色 / 计划做游戏 / 要长期改时读。
> 下面每一档都是**社区作品里真实存在的做法**（做法本身才是经验；具体某个作品有几块积木不重要，
> 想核就自己用 `lab/inspect-sb3.mjs` 量）。

## 按规模选架构（先想清楚你要哪种）

### Level 1：算法演示（几十块以内）
一个角色一个绿旗脚本完事。比如「用十几块实现缓动旋转」。**别过度设计**——不需要广播、不需要引擎。

### Level 2：功能游戏（几百到一千多块）
4-6 个角色按**职责**分：
- `System`（初始化/时钟）、`Player`、`Enemy`、`Danmaku`（弹幕克隆池）、`Hitpoint`（碰撞判定）
- 东方 style 弹幕就是这个结构：模块间广播，各自 forever+wait 主循环
- **角色命名按职责不按默认名**（Sprite1 ❌）

### Level 3：系统游戏（几千块）
开始需要**分层**和**专用模块**：
- 图层精灵组：`图层//前 / 中前 / 中后 / 后`——每层一个角色管一层的排序
- 专用子系统独立成角色：`存档`、`死亡界面`、`商店`、`检测Fps`、`过渡`（转场黑幕）
- 状态机变量：`page`（当前页）、`mod`（模式）、`target.page`——**用变量显式记录状态**，别靠「现在谁显示着」隐式判断

### Level 4：引擎派（上万块，慎入）
两种真实存在的极端做法：

**A. 三精灵引擎**（RENDER / MAIN / LOADER + canvas 扩展）
- RENDER：只管画（pen + canvas）
- MAIN：只管逻辑（列表就是它的内存）
- LOADER：只管序列化（解析文本存档码）
- 适合：工具类作品（词曲渲染、编辑器）。**职责切得干净，是这份文档里最推荐的大项目骨架。**

**B. 单精灵 ECS**（`Ent` 装全部实体逻辑 + `Draw` 专用渲染 + SFX + UI）
- Ent 一个角色装下所有实体：几百个 top-level 脚本、上百个全局变量
- 相机系统：`Cam X/Y/Zoom/Rotation/Focus` 全局变量
- 输入系统：双击检测、按住时长、滚轮状态全部做成全局变量
- 适合：真正的 RPG / 大世界。**这是「能跑」的天花板，也是维护噩梦**——上百个全局变量谁都不敢改。
  AI 不到万不得已别学这套；真要做大世界，用**列表分组**把全局变量压回几十个以内

## 通用铁律（各档位作品都这么做）

1. **初始化集中制**：一个 `_ Init` 广播，所有模块监听并复位自己的变量。绿旗重开必须回到初态（这是社区检验作品的暗标准）。
2. **广播命名即架构文档**：`_ Init` / `Start Game` / `__ PL Inv`（`__`=系统级、`_`=模块内部）。看广播列表就能画出系统图。
3. **自定义积木是唯一防重复手段**：任何出现两次的块序列都该包成 procedure，主脚本只留调度。大项目里几十上百个 procedure 是常态。
4. **列表前缀 = 命名空间**：`graph.point`、`graph.link`、`graph.chosen_point` 同属一个结构域。
5. **图层控制显式化**：入场时 `移到最前`，别依赖创建顺序（那是隐式地狱）。

## 反面教材（样本里真实存在的坏味道，AI 别学）

- ❌ 默认名满天飞：`Sprite1`、`角色1`、`变量1`——重命名是零成本的第一步
- ❌ 一个 forever 塞一两百块：拆 procedure，主链保持 10 块内
- ❌ 逻辑和渲染混在一个链里：改个动画效果要碰游戏逻辑——分角色/分 procedure
- ❌ 几十个变量叫 `_temp`、`temp2`、`:value`：临变量泛滥=没想清数据模型，该用列表结构化
- ❌ 魔法数直写：`移到 x:(47) y:(-123)` 到处复制——常量集中初始化
- ❌ 检测不到退出条件的等待：`等待 1 秒` 硬编码卡时序，改用广播信号量

## 什么时候该停下来简化（给 AI 的自觉）

- 角色 > 15 个且互相广播成网 → 该合并成「模块精灵 + 列表」
- 全局变量 > 30 → 该换列表结构体
- 同一个 forever 里 if 嵌套 > 3 层 → 该拆 procedure 或换状态机变量
- 复制粘贴的块组 > 2 份 → 该包自定义积木
