# 十个真的能照抄的写法

> 适用场景：你要从零搭一个**能跑起来**的东西（游戏循环、数据表、UI、寻路），或者正在怀疑自己的结构写歪了。
> 这些不是规范推演，是反复验证过的骨架：能跑、能撑住体量、改动时不容易连坐。
> 每条都带"怎么写"——具体到用哪几个积木、顺序、参数放哪。**没有一条是"要注意性能"这种废话。**
>
> 读法：先看"什么时候用"判断要不要，再看"怎么写"照着摆，最后看"坑"。

---

## 1. 帧率无关的主循环（先算这一帧过了多久）

**什么时候用**：任何有持续运动的东西。只要你的运动是"每帧加一个固定数"，掉帧时就会变慢——这不是性能问题，是**手感问题**，而且改起来是全局的地基。

**怎么写**（顺序不能变）：

```
① 设 frameDt = (计时器 − lastTimer)
② 设 lastTimer = 计时器
③ 如果 frameDt > 0.075 就 设 frameDt = 0.075     ← 必须有
④ 如果 frameDt < 0    就 设 frameDt = 0          ← 必须有
⑤ 设 dt = frameDt
⑥ 如果 fast = 1 就 设 dt = dt × 2                ← 可选：二倍速/赶时间模式
⑦ 调用 frame()                                    ← 真正的一帧逻辑全在这个自定义块里
⑧ 等 0 秒                                          ← 让出这一帧，别的脚本才有机会跑
```

放一个角色里、用 `event_whenflagclicked` 起一条 `control_forever`，别的地方一律不许再开第二个主循环。

之后所有运动都写成 `设 x = x + 速度 × dt`（`operator_multiply` 接在 `motion_setx` 的 X 上），**不是** `motion_changexby 1`。

**为什么**：`计时器`（`sensing_timer`）在 TurboWarp 里是真实秒数，一帧差值是 0.033 左右。乘以它以后，"每秒钟走 300 像素"在任何帧率下都成立。

**坑**：
- 不夹上限（第 ③ 步）→ 切走标签页再回来，计时器差值可能是几秒，物体一帧飞出舞台，或者直接穿墙。
- 不兜底负值（第 ④ 步）→ 用户点了停止再点绿旗，计时器归零但 `lastTimer` 还是旧的大数，dt 变成负数，所有东西倒着走一帧。
- 第 ⑧ 步 `等 0 秒` 不是"休息"，是让出时间片。少了它，这个 forever 会把整个 VM 卡在这一条脚本里。
- 你不需要"每帧都跑"的东西（定时器、倒计时）也用同一个 dt 累加，别开第二个 `wait 1 秒` 循环——两套时间基准迟早错开。

## 2. 广播名用「分类-动作」

**什么时候用**：广播超过 10 个，或者你发现自己在纠结"这个广播该叫什么"。

**怎么写**：名字一律 `分类-动作`，分类只用四个：

| 前缀 | 含义 | 谁接 |
|---|---|---|
| `init-` | 初始化，只该发生一次 | 每个需要重置状态的子系统 |
| `sync-` | 状态变了，请刷新你显示的东西 | 只管显示的角色 |
| `raise-` | 发生了一件事（点了个按钮、过了一关） | 所有关心这件事的人 |
| `warm-` | 预热/缓存，可以晚点做 | 美术、字体、音效 |

**为什么**：分类本身就是文档。加一个新界面时，你只需要想"它要跟着谁变"，然后挂到 `sync-*` 上，**不用改任何老代码**。反过来，名字随手起（"开始"、"开始2"、"开始游戏"）时，加功能必然要去翻别人的脚本。

**坑**：
- 广播名拼错**不会报错**，接收方永远不会触发。写完用 `scratch_list_scripts` 看一眼有没有对应的接收脚本，或者跑一次看它到底动没动。
- 别用 `broadcast and wait` 串流程，除非你真的需要"等这件事彻底做完再往下"。它是同步点，用多了会把一帧拉长到几百毫秒。

## 3. 数据驱动：`前缀-字段` 平行列表（一行一条记录）

**什么时候用**：有 ≥5 个同类实体，且它们的属性不止一两个（卡牌、敌人、关卡、道具、台词）。

**怎么写**：

```
卡牌-编号   [1, 2, 3, …, 61]      ← 或者干脆不建，用下标当编号
卡牌-攻击   [10, 25, …]
卡牌-防御   [0, 5, …]
卡牌-类型   ["攻击", "防御", …]
卡牌-文字   ["造成 10 点伤害", …]
```

- 每张表**等长**，第 n 项属于同一张卡。
- 取值：`item (id) of [卡牌-攻击]`。
- 加一条新记录：**每张表都 `add to list`**，一条都不能漏（漏了这张表从此错位，而且不会报错）。
- 改一条：`replace item (id) of list`。
- **删除一条：不要 `delete (id) of list`** —— 它后面所有记录的 id 全部前移，所有存着 id 的地方（克隆体私有变量、存档）瞬间指向错的东西。要么把它改成空/0 当墓碑，要么维护一张空闲索引（见第 4 条）。

**为什么**：比"一行塞一个 `a|b|c` 长字符串再 `split`"快得多，也比"每张卡建一堆变量"好遍历——因为 `length of list` 天然就是记录数，for 循环直接扫。

**坑**：表多了以后，改字段要动好几处。字段超过 ~12 个就该考虑拆成两张表（"基础属性"和"战斗属性"），别一张表塞 30 列。

## 4. 对象池 + 空闲索引（克隆体的正确开法）

**什么时候用**：子弹、粒子、敌人、飘字——任何"会反复出现又消失"的东西。**不要每帧建克隆**，那是 Scratch 里最贵的操作之一。

**怎么写**：

```
开场（只一次）：
  重复 N 次 { 克隆自己 }
  每个克隆体：隐藏；设 我的编号 = (克隆体序号)；把 我的编号 加入 [空闲索引]

取一个（要用的时候）：
  如果 (length of [空闲索引]) > 0 {
    设 i = (item (length of [空闲索引]) of [空闲索引])   ← 从**表尾**取，不是表头
    delete (length of [空闲索引]) of [空闲索引]          ← 删表尾是 O(1)
    广播「激活-<编号 i>」 或直接设一个 "请求编号" 变量让第 i 个克隆体自己认领
    显示；移到起点；状态 = 1
  } 否则 { /* 池空了：丢弃这次生成，或扩容 */ }

归还：
  隐藏；状态 = 0；把 我的编号 加入 [空闲索引]
```

**为什么**：建克隆要复制造型、变量、脚本栈；池化以后运行期只有"设变量 + 显示"，成本几乎为零。

**坑**：
- **漏还一次，池就永久少一个**，而且不会有任何报错——表现为"玩久了子弹越来越少"。
- **重复归还**同一个编号，会有两个实体抢同一个槽，表现为"有个东西原地不动、也不消失"。
- 还的时候顺手把状态/速度清掉。忘了清，下次取出来会带着上次的残留速度。
- 池大小按峰值给，不是按平均给。子弹峰值一般 20~50，不用开到几百。

## 5. 把逻辑全塞进自定义块，并且开 warp

**什么时候用**：项目一旦超过几百块，或者你发现"每帧跑不完，画面在抖"。

**怎么写**：

```
主循环（一个角色，8 块左右）：
  frameDt 那 4 行 → 调用 frame()

frame()（自定义块，勾上「运行时不刷新屏幕」）：
  调用 输入()       ← 读键盘/鼠标，只读不画
  调用 模拟(dt)     ← 移动、碰撞、状态机
  调用 渲染()       ← 摆位置、换造型、画线
  调用 音频()
```

- 每个自定义块开头**别做返回判断**（Scratch 自定义块没有返回值），要返回就用一个约定变量。
- warp 里**绝对不能有**：`forever`、`wait`、`broadcast and wait`、`glide`。有一个就把整帧卡死在那儿。

**为什么**：开了 warp 的块会一次跑完、中间不插帧。于是"这一帧的逻辑"是一个原子操作，画面不会出现"算了一半就被画出来"的撕裂；也避免了每个块之间让出时间片带来的抖动。

**坑**：warp 里跑太久（几万次循环）会让整个页面卡住一秒以上，比不 warp 更难受。重活要么分帧，要么用 `repeat` 分批 + 每批 `等 0 秒`。

## 6. 自己渲染文字（**先看背包，别从零写**）

**什么时候用**：要做中文界面、数字面板、霓虹字、或者任何"系统字体满足不了"的地方。用 `say` 气泡是撑不起 UI 的。

**先做这件事**：`scratch_backpack({ action: "list" })` 看一眼有没有 `文字引擎`。有就直接
`scratch_backpack_load({ name: "文字引擎", target: "要画字的角色" })`，然后三块积木用起来：

```
笔迹全部擦除 → 笔的颜色设为 […] → 调用 画文本 (内容, x, y, 字号)
```

它是 4 个 warp 自定义块 + 4 万多个字形（存在两张全局列表里，约 5 MB）；x/y 是文字**左上角**，字号就是字高。
细节、字形编码、加字、以及必踩的坑都在 **pen-text.md**。

**为什么别自己写**：难点不在渲染代码，在**字形数据**（一个字的笔画串是几百个字符，四万个字是几 MB 的工程量）。
自己搭的版本通常只能画 ASCII，遇到中文就露馅 —— 而中文 UI 基本躲不开。

**真要自己写**（只画数字/英文、或者要极简）：字符宽度表 + 逐字定位，排版是纯算术，别每帧去量尺寸。
坑：中英文混排一定要按字符查表，不能假设等宽。

## 7. 相机（世界坐标 − 相机坐标）

**什么时候用**：地图比舞台大、要跟随主角、要做缩放。

**怎么写**：

```
变量：camX, camY, camScale（就三个，别再多了）
每个可见实体，**只在渲染那一步**：
  设 x = (世界x − camX) × camScale
  设 y = (世界y − camY) × camScale
  设 大小 = (原始大小 × camScale)
```

**为什么**：实体的逻辑坐标永远是世界的，跟镜头无关。移动镜头 = 改 `camX`，所有东西自动跟着走，一行都不用改实体。

**坑**：别在"模拟"那一步就把坐标减掉相机——一旦你减了，碰撞检测就会用屏幕坐标去算，镜头一移动，碰撞全是错的。

## 8. 图搜索（邻接表 + 队列 + 头指针）

**什么时候用**：寻路、连通块、网络/管网、任何"从 A 能不能到 B”。

**怎么写**：

```
邻接表（一行一个节点，装它的邻居）：
  adj = [ 2 3 5 | 1 4 | 1 6 | … ]     ← 用分隔串或者 [节点, 邻居…] 的扁平编码
BFS:
  设 head = 1；清空 队列；把 起点 加入 队列
  重复直到 (head > length of 队列) {
    设 cur = (item (head) of 队列)
    设 head = head + 1                    ← 出队只挪指针，**绝不 delete 1 of 队列**
    遍历 cur 的邻居 {
      如果 (没访问过) { 标记已访问；把 邻居 加入 队列；记录 父亲 = cur }
    }
  }
```

**为什么**：`delete 1 of 队列` 是 O(n)，队列几千项时每次出队都在挪整张表——这是 Scratch 里最经典的隐性卡顿。头指针法把出队变成一次加法。

**坑**：访问标记用**另一张平行表**（`visited`），不要试图在 `adj` 里就地删——图被改坏后同一帧内还会被别的搜索复用。

## 9. 刷新分阶段（前置 / 本体 / 后置）

**什么时候用**：一帧里有多个子系统要更新，而且**顺序有依赖**（比如"先算位置，再算碰撞，最后才画"）。

**怎么写**：三个广播，按固定顺序发：

```
sync-前置    ← 读输入、算时间、清空上一帧的临时表
sync-本体    ← 移动、AI、状态机
sync-后置    ← 碰撞、结算、把结果写进显示用的表
sync-渲染    ← 只负责摆位置/换造型，不做任何计算
```

**为什么**：把"谁先算"从"角色添加顺序"变成**显式约定**。否则你加一个新角色，它在本体和后置之间的位置是随机的，就会出现"这一帧碰撞用的是上一帧的位置"这种幽灵 bug。

**坑**：阶段广播之间不要用 `broadcast and wait`——那会等所有接收方都跑完，一帧会被拉得很长。用普通 `broadcast` + 靠"下一个阶段的广播在同一个 forever 里排在后面"来保证顺序。

## 10. 一个关注点一个角色（而不是一个大角色什么都干）

**什么时候用**：动作类、有物理的、实体一多就互相打架的那种项目。你会反复遇到"这个碰撞该谁算""镜头该谁管"。

**怎么写**：把职责拆成几个**从不画东西**的角色，每个只干一件事：

| 角色 | 只负责 | 不做 |
|---|---|---|
| `物体管理` | 维护物体列表、建/销毁克隆体、分配编号 | 不算碰撞、不移动 |
| `碰撞箱` | 每帧读一遍物体列表，判定重叠，把结果写进"碰撞对"表 | 不改物体状态（让物体自己读结果改自己） |
| `摄像头` | 维护 camX/camY/camScale，按主角位置插值 | 不碰任何实体的世界坐标 |
| `移动禁区` | 一块不可穿越区域的形状数据 | 不管谁撞进来 |
| `触发区` | 进了区域该发生什么（发 `raise-*`） | 不直接改别的子系统 |

每个角色都只有一两条脚本：`sync-本体` 里读表 → 算 → 写回表。它们之间**只通过列表和广播通信**，不共享脚本。

**为什么**：一个"什么都干"的大角色会变成改一处崩三处的泥球；拆开以后，碰撞逻辑出问题只需要看 `碰撞箱` 一个角色，而且可以把 `碰撞箱` 整个换掉（换成网格法/物理扩展）而不动别处。

**坑**：拆完要保证**阶段顺序**（见第 9 条）——`物体管理` 必须先于 `碰撞箱`，`碰撞箱` 必须先于 `渲染`。顺序一旦靠"角色在列表里的位置"决定，加角色就会出幽灵 bug。

**别拆过头**：这条只在"拆出来的角色各自维护数据、不画东西"时成立。一旦一个角色**有一批要一起换的造型**，它就成了独立的资产边界，那已经不是本条说的"关注点"了 —— 两种拆法混着用就会掉进 `sprite-split.md` 里那个坑（拆成 64 个角色的作品，跨角色复制的自定义块有 49% 已经不一致）。

---

## 怎么用这十条

- 不要一次全上。**先上第 1 条**（主循环），它决定其它所有东西怎么写。
- 第 3、4 条是配套的：有池就必然有表，池里每个实体的字段就是表的列。
- 第 5 条是"什么时候该重构"的信号：主循环超过 30 块，就该把逻辑搬进 warp 自定义块了。
- 这些是**起点**，不是教条。真实作品里它们会被拆开、混用、按需变形——但骨架都是这几种。
