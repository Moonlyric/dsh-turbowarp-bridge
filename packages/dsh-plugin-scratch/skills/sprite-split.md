# 角色怎么切：一个实体一个角色，还是全塞进列表

> 适用场景：开工前决定建几个角色；或者接手一个"改一处要改七处"的项目；
> 或者发现两个角色里躺着两段一模一样的自定义块。
>
> 一句话结论：**角色 ≈ 资产边界（一批要一起换的造型），不是逻辑边界。**
> 下文所有数字都是拆开真实作品数出来的，不是估计。

---

## 1. 为什么角色是最贵的单位

- **没有跨角色函数调用**。自定义块只在自己角色里可见 —— 两个角色要同一段逻辑，只能复制，或广播。
- **没有跨角色局部变量**。A 角色的局部变量 B 看不见，想共享只能扔到舞台上当全局变量。
- **一个角色 = 一条时间线**。每帧"谁先跑"由线程创建顺序决定，**不受你控制**。
- **广播是唯一同步手段，而且不便宜**：接收方的帽子脚本每次都要重建线程。一个作品里 17 个广播每帧发送，就是每帧重建几十条线程。

所以角色拆多了，代价不是"文件多"，而是 **代码只能复制、执行顺序只能靠广播**。

## 2. 三种切法（三种都见过，都成立）

### A. 一个实体一个角色 —— 64 角色 / 10129 块

| 事实 | 数 |
|---|---|
| 前 4 个角色（植物 / 僵尸 / 子弹&饰品 / 卡片&胜利品）占比 | 5480 / 10129 = **54%** |
| ≤24 块的角色（界面小控件：绿旗 + 1~4 条接收） | 17 个，合计 288 块 = **2.9%** |
| 单角色局部变量 | 植物 **142** 个、僵尸 **122** 个 |
| 造型 | 植物 **289** 张、僵尸 **307** 张 |
| 跨角色重名的自定义块 | 15 组，最多一组在 **7 个角色**里各有一份 |
| 其中已经不一致的 | **6 组（40%）** |
| 最大广播扇出 | `结束游戏` **27 个接收方**、`显示菜单` 16 个 |

它**该这么拆**的理由只有一个：那 596 张造型。每个单位要有自己的动画帧、还要能整体换 —— **造型是拆角色的正当理由，逻辑不是**。
注意那 17 个 ≤24 块的角色：几乎全是**界面小控件**（进度条三段、门、计时器、对话框头），每个只有「绿旗 + 1~4 条接收」加几张造型，只占 2.9% 的块；还有 2 个角色一条脚本都没有，只剩造型。拆到这个粒度，**每个小控件都要自己一份"绿旗初始化 + 同步广播"样板** —— 这就是角色数量的隐性成本。

### B. 全塞一个角色 —— 4 角色 / 14461 块

| 角色 | 块 | 干什么 |
|---|---|---|
| `关卡运算模块` | **12669**（159 个自定义块） | 全部规则 |
| `地图生成模块` | 1651 | 生成地图 |
| `显示模块` | 116（165 张造型） | 只会画 |
| `fps测定模块` | 25 | — |

全局变量只有 **4 个**，列表 **154 张**（最大的 6 张各 40401 项）。
好处：函数只有一份、没有跨角色通信、改一处就是改一处。
代价：存在 8000 块的角色，定位只能靠命名前缀和编号分派。

### C. 一个逻辑角色 + N 个"只会画"的角色 —— 3 角色 / 4691 块

| 角色 | 块 | 造型 | 干什么 |
|---|---|---|---|
| `Sprite` | 2540 | 85 | 规则 + 本体/导弹/城市（都是克隆体） |
| `Renderer` | 1761 | **1** | 只画：投影、轨迹、鼠标位置（最大单块 782 块） |
| `CDPen` | 291 | **1** | 只画冷却圈（只有一个自定义块，254 块） |

**这是最推荐的形态。** 理由不是"分层好看"，是**绘制顺序**：多个角色往同一支画笔上画时"谁先画"取决于线程顺序，你控制不了；集中到一个角色后，顺序 = 脚本顺序。
（画笔的颜色/粗细/落笔状态每个角色各有一套，所以"多个角色画同一层"不会串色，但**先后顺序会串** —— 这才是要合并的原因。）

## 3. 跨角色共享代码：三条路，只选一条

### 路 1：复制（90% 的作品这么干）

- 好：调用是同步的、参数直接传、返回槽可以用**局部**变量（各角色一套，不会撞名）
- 坏：改一处要改 N 处。**实测 9 个作品、65 组跨角色同名自定义块，32 组（49%）已经不一致**

要复制就加**编号前缀**：`40检测x %s 处的地面h`、`13等待 %s 秒或游戏结束`、`9检测y %s 所处行`。
编号让"第 40 号函数"全局可搜，也顺手给返回槽起了名（见第 4 节）。

### 路 2：广播调"库角色"

```
广播并等待「lib-取地面高度」        ← 参数先写进全局变量
读 out*地面h                        ← 返回值也在全局变量
```
- 好：只有一份代码
- 坏：广播**不带参数**（全靠全局变量槽）；每调一次起一个新线程；被调方一旦 `等待` 就跨帧，异步 bug 从此开始
- 只在"一次调用能容忍一帧"的地方用：初始化、切场景、生成关卡

### 路 3：不拆，让它通用

把函数写成"传 id 进来"，全项目一份（`射弹.射弹运行（3）` 那种）。**唯一不给未来留债的做法**，前提是忍得住不按角色分家。

## 4. 自定义积木没有返回值 → `out<编号>*<名字>` 槽

两个作品独立收敛出了同一套约定，可以直接抄：

```
过程名带编号：  40检测x %s 处的地面h        ← 编号在最前面
返回槽同编号：  out40*地面h                 ← 调用完读这个变量
调用方：        40检测x (x) 处的地面h
                ……
                读 out40*地面h
```

- 编辑器里按名字排序 = 按编号排序，等于给所有函数编了目录。
- `out` 槽如果放在**角色局部**，说明这份函数是复制来的（每个角色一套，不会撞）；
  如果放在**全局**，说明真有多个角色在调它 —— 这也是事后判断"这段代码是不是共享的"最快的办法。

## 5. 实体数量是动态的（子弹 / 粒子 / 敌人）

| 放法 | 什么时候用 | 代价 |
|---|---|---|
| **克隆体** | 每个实体要独立造型/大小/特效，数量 ≲ 一两百 | 全项目共享 **300 个克隆上限**；克隆体私有变量就是它的字段；`永远` 里建克隆必爆 |
| **平行列表** | 数量几百以上，或要按图层统一画 | 删记录会让 id 错位（改成墓碑或空闲索引）；调试只能看列表，监视器帮不上忙 |
| **固定槽位池** | 数量有硬上限、要反复复用（如 384 个贴图槽） | 上限写死是对的（可预算），但要写进列表名里，否则半年后没人知道 |

判断顺序：**造型要不要一起换 → 要就克隆体，不要就列表。** 数量先看 300 这条线。

## 6. 已经拆错了怎么办（接手时的实际操作顺序）

1. `scratch_project_overview()`：看每个角色的块数。**前 3 个占 50% 以上**的项目，别按角色找功能，按过程名找。
2. 跨角色同名自定义块 = 同一段代码的多份拷贝。**改之前先比结构**：一样就直接同步改，不一样先决定以哪份为准（否则你会修好 3 个角色、留下 4 个旧行为）。
3. 新功能先问"这是哪个角色的事"。共享的就放进**已经最胖的那个角色**，别新开角色 —— 新角色 = 又一次复制。
4. **别用广播传"这一帧的中间结果"**。多一个广播就多一次线程重建；能放进同一个角色 / 同一张表就别广播。
5. 真要合并两个角色：先合并**变量和列表**（会报"变量未找到"，比合并脚本直观），再搬脚本。

## 8. 反例：一张卡一个角色（真机 12 个角色 / 444 块）

一个明日方舟同人关卡的实测数据（19 角色 / 2366 块）：

| 角色 | 块 | 造型 | 实际是什么 |
|---|---|---|---|
| `核心` | 1808 | 19 | 全部规则 + 画笔渲染 |
| `卡01` … `卡12` | **各 37**（展开 73） | **各 1** | 同一段脚本的 12 份拷贝，只有**两个数字**不同 |
| `按钮暂停/速度/撤退/技能` | 各 18 | 1~2 | 同理，4 份 |

12 张卡 = **444 块 = 全项目 18.8%**，做的是同一件事。每张卡里躺着的脚本长这样：

```
绿旗：移到 (-220 + n*40, -124)   ← 坐标写死在每个角色里
      换造型为 1               ← 只有 1 张造型，这句等于没换
      设大小为 100；设虚像为 0
绿旗：永远 { 等 0.1 秒；
      如果 (O_DEPLOYED[1] = 1)      …虚像 55 / 大小 92
      否则如果 (O_COOLDOWN[1] > 0)  …虚像 55 / 大小 96
      否则如果 (DP < 12)            …虚像 45      ← 费用写死
      否则                          …虚像 0 / 大小 100 }
点自己：CLICK_CARD = 1；广播 卡牌
```

**12 份之间的差别只有"下标 1"和"费用 12"。** 这不是"拆得细"，这是把**数据行**当成了角色。

代价三条，第三条最疼：

1. 改一个布局常量（间距 40、起点 -220）要改 12 个角色；
2. 加第 13 个干员 = 再复制一个角色 + 再改一次 HUD 排版；
3. **它真的咬过人**：这个作品的作者在生成积木时，有一份卡牌的嵌套 `如果/否则` 被建到了错误的 target
   （`KeyError: b1843`）。**12 个几乎一样的角色**放大了"绑错对象"的出错概率 —— 而这类 bug 不看运行时是查不出来的。

### 正确写法：1 个角色 + N 个克隆体 + 一个编号

```
卡片（1 个角色，12 张造型）        局部变量 号
──────────────────────────────────────────────
绿旗：  隐藏；号 = 0
        重复 12 次 { 号 = 号 + 1；建自己的克隆体 }
        号 = 0
克隆体：换造型为 (号)
        移到 x: (-220 + (号-1)*40)  y: -124
        显示
        永远 { 等 0.1 秒
          如果 (O_DEPLOYED[号] = 1)      → 虚像 55 / 大小 92
          否则如果 (O_COOLDOWN[号] > 0)  → 虚像 55 / 大小 96
          否则如果 (DP < O_COST[号])      → 虚像 45
          否则                           → 虚像 0 / 大小 100 }
点自己：CLICK_CARD = 号；广播 卡牌
```

- 块数 **444 → 约 55**；加第 13 个干员 = 改 `重复 12` 的 12 和 `O_COST` 表，**块一个不加**。
- 费用必须从表里读（`O_COST[号]`）—— 写死费用正是"一卡一角色"的起因。
- 克隆体天然保留「当角色被点击」的命中判定，不用手写点击检测。
- 12 个克隆远低于 300 上限；一排 UI 用克隆几乎是白送的。

### 判据

> **角色数应该跟"造型集合的种数"和"交互行为的种数"走，不跟"条目数"走。**

一排一样的东西（干员卡 / 道具格 / 头像墙 / 商店条目 / 关卡按钮 / 血条段）：
**1 个角色 + N 个克隆体 + 编号变量**。N 只影响克隆数，不影响块数。
只有当每一条**真的有自己的动画帧集合或自己的交互脚本**时，才值得一个角色一个。
（真要上百条、还每帧重画，再退到"一个角色 + 画笔 + 手写命中检测"，那是 §5 的列表派。）

## 9. 决策清单

1. 这批东西的造型要一起换吗？要 → 角色；不要 → 列表。
2. 数量会超过 300，或每帧上几百？是 → 列表。
3. 这段逻辑只有一个角色用？是 → 放它自己身上，别搞库角色。
4. 两个角色都要用同一段逻辑？→ 优先"合并成一个角色"，其次"复制 + 编号"，最后才是"广播调用"。
5. 需要绘制顺序稳定？→ 全部绘制集中到一张造型的角色里，靠脚本顺序，别靠广播。
6. 需要"一帧内算完"？→ 必须在同一个角色里（跨角色就只能靠广播，跨帧）。
7. 一排 N 个一样的东西（卡片 / 按钮 / 道具格）？→ **1 个角色 + N 克隆 + 编号**，别一个角色一个（§8）。
