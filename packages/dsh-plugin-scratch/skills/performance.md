# 性能与稳定：让 Scratch 项目不卡不崩的边界

> 适用场景：有弹幕/粒子/大量克隆/pen 绘制时必读。
> 来源：能跑动「几十个角色的弹幕」和「几 MB 体量应用」的项目们共同遵守的纪律。

## 宿主差异（先搞清楚你跑在哪）

| 能力 | 原版 Scratch (scratch.mit.edu) | TurboWarp (turbowarp.org) |
|---|---|---|
| 克隆体上限 | **300 硬限**（超了生成静默失败） | **默认无限制**（TA 校准 2026-10-16） |
| 帧率 | 30fps | 更高（另有 turbo 模式），勿假设固定 30fps |
| TW 专属扩展 | 无 | canvas 操作、更强编译优化等 |
| pen/music 等常规扩展 | 有 | 有 |

**决策规则**：本桥的宿主是 TurboWarp → 克隆上限不是硬约束；但**要发布回 scratch.mit.edu 社区的项目仍受 300 限**，跨宿主项目按 300 保守设计。另外 TW 无克隆上限 ≠ 无限白嫖——几千个克隆体照样吃内存拖帧率，死亡纪律仍然成立。

## 硬限制（两边都一样的，没有商量）

| 限制 | 数值 | 后果 |
|---|---|---|
| 列表显示条目 | 视图限制 | 存数据没事，只是显示不全 |
| 嵌套列表 | 不支持 | 社区用「字符串拼接+分隔符」模拟 |
| 递归深度 | ~150 层（估算） | 超了栈溢出，死循环递归尤其快 |
| 造型尺寸 | 240x180 舞台外会被裁 | 大图用缩放显示 |

## 性能十条（那些跑得动的作品都这么做）

1. **克隆体必须自带死亡条件**：`重复执行直到 <出屏 或 命中>` 然后 `删除此克隆体`。TW 下没有 300 硬限，但只生不死的克隆照样把内存和帧率拖死——这是性能问题不是配额问题。
2. **pen 重绘场景每帧先 clear**：血条/HUD 每帧 `全部擦除` 再画。反之残影/轨迹类就是**不**清除。混着用前想清楚哪层是哪个策略——分两个精灵（一个清一个不清）。
3. **forever 必带 wait**：`重复执行 { ... 等待 (0.02) 秒 }`。无 wait 的 forever 是 UI 冻结第一杀手（TurboWarp 会提速但行为依赖帧率，兼容 scratch.mit.edu 就必须等）。
4. **碰撞检测做粗筛**：先比距离 `<[与 ... 的距离] < 100>` 再 `碰到 [...]？`。社区弹幕游戏的常见做法：玩家判定只用一个小 Hitpoint 精灵，弹幕判定用坐标数学（列表流派的本质优势）。
5. **列表越长越别动头部**：删除第 1 项 / 在第 n 项前插入 都是 O(n)，几千项时一次就是几毫秒。见下面那张代价表。
6. **画笔粗细/颜色切换有开销**：同帧同参数的 stamp 排在一起画。
7. **隐藏的精灵也在跑脚本**：不用的角色 `隐藏`（looks_hide）+ 停它的脚本（广播控制），别留着 forever 空转。
8. **每帧发的广播 = 每帧重建的线程数**：`广播` 的每个接收方帽子都会新建一条线程。一个接收方 27 个的广播每帧发一次，
   就是每帧 27 次线程创建（真实作品里就是这么干的，代价已经写进它的风险清单）。
   判据：**每帧都要发的状态同步**别用广播，改成"一次广播 + 各角色读同一个变量/列表"。
9. **矢量造型每次缩放档位变化都要重新栅格化**。造型多、又会被缩放（UI 弹入、镜头拉远）的项目，
   第一次显示时掉帧就是这个原因。两条解法：预热（见 **boot-pipeline.md**）或者干脆用位图造型。
   反过来：位图造型放大就糊 —— 别在位图素材上做"缩放到 300%"的效果。
10. **warp 的边界**：`运行时不刷新屏幕` 里的循环一次跑完，**跑太久就是整帧卡住**（不是平均分摊）。
    所以 warp 里只能放"一次性能算完"的活（生成关卡、算路径、画一批字），不能放"每秒都要算一部分"的活。
    warp 里也不能 `等待` / `广播并等待`（语义直接失效）。长循环要自己切成批：每次调用算 N 个，下一帧再算 N 个。

## 列表操作的真实代价（几千项时决定生死）

下表的 n = 列表长度。这几条都**不会报错**，只会让帧率慢慢掉下来：

| 操作 | 代价 | 该怎么做 |
|---|---|---|
| `第 n 项` / `替换第 n 项` | O(1) | 随便用 |
| `删除第 1 项` | **O(n)** 整个表前移 | 出队只挪头指针（`头 += 1`），绝不删第 1 项 |
| `在第 n 项前插入` | **O(n)** 整个表后移 | 只在必要时用；贴图池那种"每帧插入几十个、n 只有几百"的场景才划算 |
| `包含` / `编号` | **O(n)** 逐项比字符串 | 上万项的表绝对不能用它查；用坐标算下标，或者另建一张"名字→下标"的索引表 |
| `长度` | O(1) | 放心 |

```
❌ 每帧 删除第 1 项 于 [子弹]        // 130 项的表，每帧搬 130 次
✅ 头指针 += 1，取项时用 第 (头 + i) 项   // 数组越用越脏，定期压缩一次
```

## 每帧块数：只看一个数就够

`scratch_project_overview` / `lab/dissect.mjs` 都会给"每帧块数"（所有 forever 循环体的块数之和）。
经验线：**几百块 = 很宽松；上千块 = 开始需要拆 warp、把碰撞挪去列表一次算；两千以上 = 一定掉帧**。
真实作品里 1984 块/帧的那个已经在风险清单里写着"离 33ms 的帧预算不远"。

## 稳定性三律

1. **绿旗重开全复位**：`_ Init` 广播清列表（`删除 [全部] 项于`）、复位变量、隐藏所有临时精灵、`计时器归零`。用户测试你作品的第一件事就是连点绿旗。
2. **广播风暴防护**：广播接收器里不再广播同名/互触发的消息对（A 听 B 发、B 听 A 发 = 死循环风暴）。用「状态变量守卫」：`如果 <非进行中> 那么 { 设 进行中=1, ..., 设 进行中=0 }`。
3. **停止一切是急救键**：`停止 [全部]`（control_stop all）能一键灭火。调试期间在角落放一个「重置」广播。

## dsh 场景特化（AI 用桥改项目时）

- 你改完块后项目在编辑器里**不自动重跑**——`scratch_run({action:"greenflag"})` 自己点，别让用户代劳；
  要确认真的跑起来了看 `scratch_state` 里那个角色的坐标/变量有没有变（`running:true` 不算证据）
- 大项目（>2000 块）先 `scratch_read_script({summary:true})` 拿结构，再按 `scriptId` 读单段；
  `scratch_snapshot` 是整项目 project.json，大项目别整份拉（token 会爆）
- 性能问题用 `scratch_profile({seconds:3})` 量（读 VM 自己的步进耗时），别信项目里那个 `fps` 变量
- **量出"慢"之后要用归因说清"哪条脚本慢"**：`profile` 默认带 `attribution`，先看 `granularity`：
  - `block`（编译器关着）：`hot` 每条含 `target` / `blockId`（脚本根，可直接
    `read_script({scriptId})`）/ `hat` / `pct` / `topOpcodes`。`waitPct` 是「等 N 秒」这类空转占比
    —— **别把 wait 当热点优化**，那是设计不是 bug。
  - `script`（**编译器开着，TurboWarp 桌面版默认**）：脚本被编译成 JS 跑，线程栈不移动，
    所以只能给「哪条脚本的线程活着」（`scripts`），**拿不到块级热点**。要用块级就让用户在设置里
    关掉「编译器」再量，或者用 `stepMs` 做改前/改后对比 —— 这种模式下**别编造"哪个块最慢"**，
    也**别把 100% 挂在帽子块上当成热点**。
  - 没线程在跑时归因为空并提示先点绿旗（先 `scratch_run` 再量，否则数字是假的）
- **`stepMs` 恒等 33.33 不是"跑满了"**，是被 30fps 的帧帽闸住。`profile` 会给
  `frameCapMs` / `atFrameCap` / `headroomMs`：顶到帧帽时它明说"看不出还有多少余量"，
  这种时候只适合做**改前/改后对比**，别拿它算"还剩多少性能"。
- 改动前快照是自动的（scratch_add_blocks 内置），但**连续多次改**建议口头告知用户每步要改什么——preview 档的存在意义就是这个
