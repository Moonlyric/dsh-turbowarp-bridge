# 渲染队列：所有东西都往一张有序表里塞

> 适用场景：画面里的东西来自**好几个互不相干的子系统**（地图、角色、子弹、特效、UI），
> 你要它们叠放顺序稳定、又不想每帧对所有东西排序。
>
> 来源：一个 14500 块、**只有 4 个角色**的 2.5D 射击作品。它的做法不是"每个子系统自己画"，
> 而是**各子系统只往一张「贴图池」里登记，最后一趟画完**。

---

## 1. 结构：一张表 + 一组插入过程

```
贴图池（平行列表，固定容量 384 槽）：
  贴图.x / 贴图.y / 贴图.大小 / 贴图.朝向 / 贴图.颜色 / 贴图.亮度 / 贴图.虚像 / 贴图.图层

◇ 贴图.加入贴图(ID, x, y, 大小, 朝向, 颜色, 亮度, 虚像, 图层, …)
  i = 二分查找图层(图层)              ← 找到"第一个图层比我大的位置"
  在贴图池的第 i 项前插入 贴图(...)    ← 插入过程中整列一起后移
◇ 贴图.在最后加入贴图(…)              ← 不排序的快速版本（同层、顺序无所谓时用）
◇ 贴图.加入空贴图(数量)               ← 预分配槽位
◇ 贴图.删除所有贴图                   ← 每帧开头清空
```

要点：

- **插入时保持有序**，绘制时就是从头到尾一趟 —— 不需要每帧排序。插入是 O(n) 搬列表，但一帧插入几十个、n 只有几百，比排序便宜也更稳定（同层内的先后顺序不会因为排序算法而跳）。
- **二分查找只为"插到哪"服务**。`贴图.二分查找图层` 返回插入点，插入过程负责把这一层往后挪。
- **固定容量 384**：等于告诉作者"一帧最多画 384 个东西"。这是**有意的上限** —— 比动态扩容好排查（超了就丢，不会悄悄卡）。

## 2. 一趟画完

```
◇ 显示贴图(n)
  重复 n 次 {
    换造型 (贴图.ID 的第 i 项)
    移到 (贴图.x[i], 贴图.y[i])
    大小/朝向/颜色/亮度/虚像 ← 分别设
    图章（stamp）或 交给克隆体显示
  }
```

**用 `图章` 还是克隆体**：一帧几百个东西用克隆体要几百个克隆（直接撞上限），所以是"**一个角色反复换造型 + 图章**"。代价是每帧重盖一次（清屏后），好处是数量只受块数限制。

## 3. 实体也用同一套表

```
角色.  id / 阵营 / x / y / xv / yv / 标签 / 朝向 / 碰撞半径 / 血量 / 状态 …（10 列）
射弹.  id / 阵营 / x / y / 方向 / 速度 / 半径 / 高度 / 状态 / 伤害 …（9~18 列）
特效.  id / x / y / xv / yv / 大小 / 虚像 / 高度 / 状态 / 朝向 / 亮度 / 图层 / 特殊状态 …（56 列）
```

每种实体一套平行列表（第 n 项 = 第 n 个实体），**互不干扰**，各自的"类型"再决定行为。这就是 `proven-patterns.md` 第 3 条的放大版：一个项目里 200+ 张表是正常的，名字带前缀就不乱。

## 4. 类型编号 → 同名过程 → if 链分派

```
◇ 射弹.射弹运行（1）(a, b)   ◇ 射弹.射弹运行（2）(a, b)   ◇ 特效.特效运行（21）(id) …
调用处：
  如果 (射弹.类型[i] = 1) { 调用 射弹.射弹运行（1）(…) }
  如果 (射弹.类型[i] = 2) { 调用 射弹.射弹运行（2）(…) }
  如果 (射弹.类型[i] = 3) { 调用 射弹.射弹运行（3）(…) }
```

**编号进过程名**，一眼就能对上：改"三号子弹"就只碰 `射弹运行（3）` 一个过程，不用在 800 块的 if 里翻。
Scratch 没有"按名字调用"，所以分派层还是 if 链 —— 但**分派层很薄**（一条一个 `如果`），逻辑全在过程里。这是"表驱动"在 Scratch 里的现实形态。

## 5. 网格地图：201×201 就是一张 40401 项的平行表

```
地图.id / 地图.可通行？ / 地图.显示类型 / 地图.亮度衰减 / 地图.亮度倍数 / 地图.物体占用i
每张 40401 项 = 201 × 201
```

- **一维数组存二维网格**：下标 `(y × 宽 + x)`，或者干脆按行顺序整块铺。遍历用两层 `重复`，取值用 `第 (y×宽+x) 项`。
- **一张网格 = 多张等长表**，每张管一个属性（通行性 / 显示类型 / 亮度）。加一个属性 = 加一张 40401 的表，不动任何已有代码。
- **双缓冲**：有 `地图生成.暂存表` 和 `地图.*` 两套，先算完暂存再整体写回 —— 否则"边生成边读"会读到半成品，表现是地图上出现奇怪的洞。
- 40401 项的表**别用 `包含` / `编号` 查**（O(n)），要用坐标算下标。这是这套结构能跑的前提。

## 6. 这套的代价

- **一切都在列表里**，所以"这个角色为什么不动"永远要去表里看第 i 项 —— 监视器帮不上忙，得靠 `说`/调试列表。
- 4 个角色听着很美，但那 4 个里有一个是 8000 块。**改的时候要能忍受在一个巨型 if 里定位**。缓解：过程名带编号前缀（第 4 节），靠搜索而不是靠肉眼。
- 容量上限（384 槽 / 201×201 / 每类实体几十个）到处都写死。**写死是对的**（可预算），但要写在注释或列表名里，不然半年后没人知道上限是多少。

## 7. 什么时候用它

- 同屏几十个以上会动的东西，且来自不同子系统 → 值得。
- 只有十几个对象 → 直接一个角色一个对象，别上这套。
- 需要**每帧整体重画**（图章法）还是**各自移动**（克隆体法）是两条路：前者数量只受块数限制、后者受克隆上限限制；这套作品选了前者，因为它是 384 个并存的画面。
